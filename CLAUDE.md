# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository purpose

This is a sandbox/starter repo for experimenting with Claude Code on the web. It is not a single application — it's a loose collection of independent, self-contained demos and mini-projects at various levels of completeness. Treat each top-level item (root site, `demo/`, each folder under `projects/`) as its own isolated context; changes in one should not assume shared tooling, build systems, or dependencies with another.

## Structure

- **Root site** (`index.html`, `css/styles.css`, `js/main.js`) — a static, dependency-free HTML/CSS/vanilla-JS marketing page ("BlockCraft Guide"). No build step: open `index.html` directly or serve the directory statically. `js/main.js` is an IIFE handling mobile nav toggle, scroll-spy nav highlighting, a back-to-top button, and accordion-style FAQ items.
- **`demo/`** — standalone HTML demos (e.g. `motion-hero-demo.html`) with vendored JS libraries in `demo/vendor/` (e.g. `motion.bundle.js`). These are single-file, open-in-browser demos, not part of the root site's build.
- **`connect-apps-plugin/`** — a Claude Code plugin (own `.claude-plugin/plugin.json`) providing three slash commands — `/connectors-list`, `/connectors-find`, `/connectors-troubleshoot` — for inspecting the status of Claude's app connectors (Slack, Notion, Linear, Gmail, etc.) from inside a session. Load it standalone with `claude --plugin-dir ./connect-apps-plugin`. The commands are read-only: they report connector status via the `ListConnectors`/`SearchMcpRegistry`/`SuggestConnectors` tools and point the user at claude.ai's connector settings; they never connect, disconnect, or authenticate anything themselves.
- **`projects/`** — independent sub-projects, each with its own README and conventions. Don't assume conventions from one apply to another:
  - **`prompt-engineering-mentor/`** — a repo-based prompt-engineering course, not code. `MENTOR.md` holds the portable mentor system prompt (with annotations on why it's designed the way it is); `curriculum/` holds numbered lesson modules (work 01-02 in order, then 03-04 as a pair, then 05-06); `prompt-library/` is an index of proven prompts with a tagging schema (use case / format / strength) — entries only get added after being tested against real inputs, per `prompt-library/README.md`; `sessions/` logs one file per mentoring session using `_TEMPLATE.md`. When editing this project, follow its own ground rules (always explain *why* a prompt change was made; label behavioral claims as documented/widely-reproduced/untested).
  - **`snapsite-website/`** — a static marketing site (`index.html`, `SnapSite.jsx` reference component) for a fictional field-photo/inspection app, plus a small live backend in `server/`: an Express server (`server/index.js`) exposing `POST /api/draft-report`, which streams a Claude (`claude-opus-4-8`) completion via SSE to turn field notes into a draft inspection report. Run it with `cd projects/snapsite-website/server && npm install && export ANTHROPIC_API_KEY=sk-ant-... && npm start`, then open `http://localhost:3000`. Without the server running, the front-end demo falls back to a canned sample draft. The system prompt in `server/index.js` enforces a strict rule: never invent facts not present in the notes, and the output is always `status: "needs_approval"` (nothing is auto-saved). Both the backend (`server/index.test.js`) and the front-end markdown/SSE logic (`index.test.js`, run from the repo root via vitest) have automated tests — see Testing below.
  - **`location-map-demo/`** — a self-contained Vite + React + TypeScript + Tailwind (shadcn/ui conventions) subproject embedding a draggable/3D-tilt `LocationMap` component. Fully isolated tooling: `cd projects/location-map-demo && npm install && npm run dev` (port 5173). Ships its own `vercel.json` and is meant to be deployed as a *separate* Vercel project with Root Directory set to `projects/location-map-demo` — it does not share the repo-root static-site deployment.
  - **`water-pipe-configurator/`** — a React + Vite 3D product configurator for water main pipes/fittings, using `@splinetool/react-spline` for the 3D scene. `cd projects/water-pipe-configurator && npm install && npm run dev` (port 5173). The Spline scene URL and configuration options (material, diameter, fitting type) live in `src/App.jsx`.

## The Zeus prompt-engineering pipeline

`.claude/agents/zeus.md` defines a subagent meant as the first stop for messy, half-formed requests. It drives nine slash commands in `.claude/commands/` in a fixed sequence, each stage's output feeding the next: `/prompt-master` (raw input → task spec) → `/grill-me` (resolve open questions) → `/how-to` (execution roadmap) → `/48` or `/fable` (model-specific polish — pick one, not both) → `/personal-voice` (match the user's writing style) → `/anti-ai` (strip AI writing tells, using the `stop-slop` skill if available) → `/write-a-skill` (package as a reusable skill, unless it's a one-off) → `/handoff` (final handoff doc). Each command file is self-contained and can also be invoked directly outside the pipeline. Don't skip stages when running the full pipeline — the sequence is the point, not just the final output.

## Agent skills

- `.claude/skills/` and `.agents/skills/` hold installed Claude Code / Codex agent skills (design, UI, brand, Vercel, animation, writing-guidelines, `stop-slop`, etc.), tracked via `skills-lock.json` (records each skill's upstream GitHub source and content hash). These are vendored dependencies, not application code — don't hand-edit files under these directories; they'd be overwritten by the skill manager.
- `.claude/skills/nano-banana/` is one exception: a repo-local, hand-maintained skill (not in `skills-lock.json`) for generating/editing images with Google's Nano Banana models, with its own `scripts/generate.py` and preset library. It requires `GEMINI_API_KEY`. Its Python deps are auto-installed on session start via the `SessionStart` hook wired in `.claude/settings.json`, which runs `.claude/hooks/install-skill-deps.sh` (idempotent — checks whether `google.genai` already imports before installing anything).
- `skills/3d-web-experience/` is a second, separate top-level skills directory (distinct from `.claude/skills/` and `.agents/skills/`) and is also *not* tracked in `skills-lock.json`. It's a single hand-added `SKILL.md` (source: `vibeship-spawner-skills`, Apache 2.0) covering Three.js / React Three Fiber / Spline / WebGL work — most directly relevant to `projects/water-pipe-configurator`.

## Deployment

- `vercel.json` deploys the repo as a static site with no build/install command (`outputDirectory: "."`) — the root `index.html` is the deployed artifact. `.vercelignore` excludes non-site content from the deploy.
- `projects/location-map-demo/` deploys as its **own, separate** Vercel project (its own `vercel.json`, Vite preset) — see that project's README for the Root Directory setup. `projects/water-pipe-configurator/` can similarly be deployed standalone but has no `vercel.json` of its own yet.

## Python dependency

- `pyproject.toml` declares one dependency, `google-antigravity` (the Google Antigravity SDK for building Gemini-based agents), installed via a venv + `pip install -e .` (per `README.md`). It must be installed with `pip`, not just cloned, because its PyPI wheel ships a compiled runtime binary. Import it as `from google import antigravity` — the bare `antigravity` name collides with Python's stdlib easter-egg module.
- Windows contributors have two setup scripts (`.ps1` + `.bat` pairs, see `WINDOWS_SETUP.md` and `UV_SETUP.md`): `setup.ps1`/`setup.bat` install Git via `winget`; `setup-uv.ps1`/`setup-uv.bat` install [`uv`](https://docs.astral.sh/uv/) as a faster `pip`/`venv` replacement for the step above.
- `NEUROLINK_INSTALLATION.md` and `GRAPHIFY_INSTALLATION.md` are standalone install guides for two optional third-party tools (`@juspay/neurolink`, a multi-provider LLM SDK; `graphifyy`, a codebase-to-knowledge-graph CLI/assistant-skill). Neither is a dependency of anything in this repo today — they're reference docs for contributors who want to add them, not something already wired in.
- `.mcp.json` registers one local MCP server (`claude-custom-tools`) pointing at an absolute Windows path under a specific contributor's home directory. It will not resolve on other machines/environments — treat it as personal, machine-local config rather than a repo-wide dependency.

## Testing and verification

Verification is project-specific — there's no single command that covers the whole repo:
- **Root-level vitest suite** (`package.json` + `vitest.config.js`, jsdom environment): `npm install && npm test` from the repo root runs `js/main.test.js` (nav toggle, FAQ localStorage, ARIA/keyboard nav, markdown-render XSS escaping, form validation) — other useful scripts: `npm run test:ui`, `npm run test:coverage`. **Important:** these tests do not import `js/main.js` or `index.html`'s inline script directly — they re-implement the same logic as standalone functions inline in the test file and test those copies. When you change behavior in `js/main.js` (or the equivalent inline script in `projects/snapsite-website/index.html`), you must update the matching reimplementation in the `.test.js` file too, or the tests will keep passing against stale logic. `TEST_COVERAGE_IMPROVEMENTS.md` documents what this suite covers and what's still planned.
- `projects/snapsite-website/index.test.js`: same vitest run as above (matched by the root `**/*.test.js` glob, `**/server/**` excluded) — covers the front-end's markdown renderer, form validation, and SSE event/stream parsing, with the same "reimplemented copy, not imported source" caveat.
- `projects/snapsite-website/server`: has its own independent test suite — `cd projects/snapsite-website/server && npm install && npm test` (Node's built-in test runner + `supertest`, against a mocked Anthropic client — no `ANTHROPIC_API_KEY` or network access needed). Covers request validation, prompt assembly, SSE event framing, the `needs_approval` invariant, and the request body size limit. Run this after touching `server/index.js`.
- Root site / `demo/`: open the HTML file in a browser and check it manually beyond what the vitest suite covers — there's no build step.
- `projects/location-map-demo` and `projects/water-pipe-configurator`: no automated tests; verify with `npm run dev` and manual browser checks, and `npm run build` for a type-check/production-bundle sanity check (location-map-demo only).
- `projects/prompt-engineering-mentor`: "testing" means running the prompts in `prompt-library/` against a real model and checking output against the criteria described in `prompt-library/README.md`, not automated tests.
